Scraping Adversarial Municipal Portals

Building-permit data is public by law and adversarial in practice. The dangerous failure is not the portal that blocks you. It is the portal that answers cheerfully and wrong, so a broken scraper and a quiet city produce the same number: zero.

The Challenge

Every California city publishes its building permits, and almost none of them publish the same way. The San Francisco Peninsula alone runs eTRAKiT (on at least two incompatible vendor forks), Tyler Technologies' Energov and Civic Self Service, Accela, Clariti, PermitStack, one municipal open-data feed, and one city whose only complete record is a monthly report it posts as a document. Searches are login-gated, JavaScript-rendered, and driven by ASP.NET postbacks that rewrite the form under you. Two portals in the set answer to a browser and not to a client library.

That is the visible difficulty, and it is the easy half. A blocked request is loud: it throws, the run goes red, somebody fixes it. The failures that actually cost you are the ones that return a well-formed answer to a question you did not ask.

Failure one: the empty list that looks like a quiet month. One city's portal login was being rejected on every run. The scraper printed a warning, returned an empty permit list, and the pipeline reported success. A city we actively cover disappeared from the product for weeks and nothing alarmed. Then the absence did what absences always do: it turned into a zero. The city's demolition-permit count rendered as 0, indistinguishable from a city that genuinely filed none, and that zero reached public copy written for Peninsula builders who would have known on sight that it was false.

Failure two: the result set that is not the answer. Every eTRAKiT host caps a search result. It applies the cap before sorting, it emits no error, and once the grid's page size is raised past the cap the pager that would have read "page 1 of 5" simply disappears. A truncated result set is byte-for-byte indistinguishable from a complete one. Worse, the rows it keeps follow the portal's own internal order, which skews heavily oldest-first, so the truncation drops the newest permits: the only ones a recent-activity scrape exists to find.

What We Built

AddressIntel's permit layer is a fleet of nine scrapers across eight portal platforms, running Selenium and undetected-chromedriver on a self-hosted runner, plus a document-ingest path for the cities that will not be scraped at all. As of September 16, 2026 it holds 187,838 permits across 27 jurisdictions, of which 177,522 carry an assessor's parcel number and 128,324 carry a declared valuation. Those numbers are the easy part to report. The engineering worth describing is the part that decides whether to believe them.

1. Measure the cap; never assume it

Because nothing on the page announces truncation, the size of the result set is the only tell available, and it has to be read before anything is trusted. Each host's cap was measured directly on August 25, 2026, one query per host, page size raised to 2000 so the whole set arrived at once:

Redwood City10001000 rows, 743 of them from 2015

The cap is not uniform. It ranges from 100 to 1000 across four hosts of nominally the same product, so it cannot be hardcoded once and forgotten. It is also not a page-size artifact: page one of the un-resized grid reports "page 1 of N" with N times the page size equal to the cap exactly, and raising the page size past the cap returns the cap with no pager at all.

The obvious workaround does not work either. Sorting a saturated Hillsborough search by issued date descending, which is precisely what the scraper's own sort helper does, still returns the same 500 rows with a newest date of 2026-04-22, while the city has been issuing permits continuously since. Sorting reorders the survivors. It does not change which rows survived.

Two hosts in the fleet are login-gated and their caps are therefore unmeasured rather than absent, which is a distinction worth encoding. An unmeasured host must not be treated as an uncapped one. For those, the fallback test is a total landing exactly on a round number, and it is a real signal rather than a superstition: a result set is a count of permits a city happened to issue, and that count landing on exactly 500 by coincidence is far less likely than it landing there because something clipped it. 

def etrakit_is_saturated(total_rows, url=None, cap=None):
    """True when a result set of `total_rows` is sitting on its host's cap.

    Saturated means TRUNCATED: the portal returned as many rows as it will
    ever return, so there are almost certainly more records matching the
    search than came back, and the ones missing are the newest.

    Deliberately >= rather than ==: a host that raises its cap, or one whose
    cap was measured low, must still trip this.
    """
    if total_rows is None:
        return False
    cap = cap or etrakit_result_cap(url)
    if cap:
        return total_rows >= cap
    return total_rows in ETRAKIT_ROUND_CAPS

2. Find the one bucket the platform cannot truncate

Detecting truncation is only useful if there is something better to do than report it. The standard answer, bisect the query until each half fits, is unavailable here: the search offers one criterion and five operators (BEGINS WITH, CONTAINS, EQUALS, AT LEAST, AT MOST), there is no BETWEEN and no second field, the string operators reject a partial date outright, and AT MOST truncates from the same end, so an AT MOST query on the Atherton host comes back with 100 rows whose newest is 2008-04-28.

That leaves EQUALS on a single calendar day as the only bounded bucket the platform offers, and it turns out to be an excellent one. Measured across the four date-search hosts, a single day returns 5 to 22 rows against caps of 100 to 1000. A bucket that small cannot be silently truncated, which converts an unanswerable question into an answerable one at the cost of one postback per day walked.

The walk runs newest-first on a 45-day budget, because each day costs a postback and its settle time, and the freshest permits are the ones worth spending the budget on. The budget is deliberately a budget and not a window: whatever it does not reach is named explicitly in the run log and recorded as a source failure rather than being allowed to vanish. A historical backfill asks for 1825 days, which this path will not walk, and saying so out loud is the entire point. The alternative is a backfill that returns the portal's oldest 500 rows and calls itself complete.

One further distinction earns its keep: a saturation the day-walk fully recovered from costs time, not data, and is therefore not recorded as a failure. Only days the walk could not cover are. A busy city would otherwise red the pipeline twice a day forever, which is the alarm-nobody-reads failure mode the health gate exists to prevent.

3. An alarm you would still read on day 400

The health registry records only failures the scrapers know about: a rejected login, an unreachable portal, a saturated search that could not be recovered. Breakage is never inferred from a low permit count. A quiet city and a broken scraper both produce zero permits, and guessing between them is how you build an alarm that cries wolf and then gets ignored. If a scraper cannot tell you it failed, that is a gap in the scraper, not something to paper over in the gate.

Three implementation details follow from taking that seriously.

  • Failures flush on every failure, not at the end of the run. The scrape executes under a timeout that terminates it when the budget expires, routinely. Anything saved only at the end is lost exactly when a slow, failing source is the likeliest cause.
  • The gate runs last, after the sync and the data-store save. The run goes red, but every byte the scrape did manage to collect is already persisted. A red run that kept its data is the goal; a green run that quietly lost a city is the thing being fixed.
  • Known-unscrapable sources report without reddening the run. Where the fix is a new data source rather than a retry, a permanent red is just a switched-off alarm. Entry into that list requires a tracked issue and a stated reason, and nothing else.

The retry policy is drawn on the same line. A timeout, a stale element reference, an intercepted click, a grid that did not re-render, an ASP.NET postback that never landed: these differ between two runs against unchanged markup, so they get one more attempt with a fresh driver. Two red runs in August 2026 were exactly this, one dying on an index error and one on a renderer timeout, both with runs ninety minutes earlier that had walked the identical pages to a clean finish, and both with their sync and data-store save already succeeded. They were red purely on an exit code.

NoSuchElement is pointedly excluded from that list. An element that is simply absent is the signature of a portal whose markup changed, which is real breakage and must red the run on the first attempt rather than being retried until it looks intermittent.

Above the per-source gate sits one inference that is safe to make. One quiet city is ordinary. Every city sharing a single scraper going quiet at once is a fact about the shared code, not about the cities, so a platform whose every source came back empty is reported as a known failure.

4. Knowing when scraping is the wrong answer

One town's portal has no issued-date search at all, only permit number and site address. A number-walk is technically possible; the town's permits carry year-prefixed series identifiers that the fleet's number-walk path already enumerates elsewhere. It is still not the fix, because that portal's public detail panel carries no declared valuation and no parcel number, and declared valuation is the field the town is carried for. A number-walk would restore row count while losing the column that matters, at roughly thirty-six seconds per permit. The route out is a recurring public-records request instead: one delivery carried $309M of declared valuation across 2,405 of the town's 5,128 permits.

That entry in the registry also carries its own correction, which is the part worth keeping. It used to assert that the number-walk was impossible because the town's permit identifiers were pure numeric strings with no series prefix. They are not. The claim had been written while the town had zero scraped rows and nobody had yet seen a real permit number from it, and it survived until a records delivery revealed the actual format. An assumption made in the absence of data reads exactly like a measurement once it is written down in a code comment.

A smaller instance of the same discipline: the results grid clips long descriptions to thirty characters server-side, with a literal ellipsis and no title attribute holding the full string, so the complete value is genuinely not on the page. The ellipsis is kept rather than stripped. It is the only honest signal that the stored value is a prefix, and stripping it would make a clipped string indistinguishable from a complete one. Full strings arrive later from the sources that print them whole, and the writer never overwrites a value it already holds, so a clipped scrape cannot regress a complete record.

What It Shows

Finding signal in data that is public in principle and obstructed in practice, and being able to state which parts of it are trustworthy. The scraping is ordinary engineering. The part that is rare is the instrumentation around it: a pipeline that distinguishes a failure from an absence, refuses to read a truncated answer as a complete one, and reports the gap it could not close rather than emitting a confident number over it.

What It Proves to a Client

That a dataset assembled from hostile, fragmented public sources can carry a defensible claim about its own coverage. Anyone can produce a permit table. The question a buyer should ask is what happens the week a vendor changes a form control, and whether the answer is a loud failure or a silently shortened table that still renders a chart. Here the answer is written down, measured against live portals, and enforced in a gate that runs after the data is already saved.

It also shows the cost of the alternative. A scraper that cannot tell you it failed produced a zero, that zero became a published statistic, and the fix was not a better scraper. It was teaching the pipeline the difference between "none" and "unknown".

Reconstructing a Wallet's Journey Across DEX Frontends

The Challenge

A product analyst asks a simple question: after someone swaps on our frontend, where do they go next, and where did they come from? On a normal app that is a session query. On-chain there are no sessions. There is no user ID, no login, no ordered clickstream. There is one wide, flat table of trades, each row a swap by some wallet at some block time, with no notion of "before" or "after" attached to it. The ordering that a journey is made of does not exist in the data. It has to be constructed.

That construction is where the useful signal lives. Which frontend feeds which. Where a wallet lands right after it leaves a platform. How long it dwells before the next swap. Whether a burst of volume on a new interface is fresh users or the same wallets rotating over from an incumbent. None of that is a column you can select. And the moment you want it on more than one chain, a naive approach reaches for Dune's cross-chain evms.* tables, which span billions of rows and bill accordingly. The hard part is reconstructing an ordered, per-wallet journey out of an unordered log, and doing it across four chains without the query cost running away from you.

What We Built

The Multi-Hop Origin Trace: a window-function pass that turns the flat trade log into a directed graph of frontend-to-frontend transitions. The core is one idea. Partition every trade by the wallet that sent it, order those trades by time, and let each swap look at its own neighbors. LAG reads the frontend the wallet used on its previous swap; LEAD reads the one it used next; a second LAG on the timestamp measures the gap between them. A row that knew nothing about sequence now carries its own before and after.

The window-function core

Once each swap knows its previous and next frontend, aggregating the transitions is a group-by. Self-transitions (a wallet making two swaps in a row on the same interface) are dropped, because a journey is about movement between frontends, not repeat activity on one. What remains is a ranked edge list: for every ordered pair of frontends, how many wallets crossed from one to the other, and how long they waited on average before doing it. 

-- Multi-Hop Origin Trace: reconstruct each wallet's ordered path between
-- frontends from an unordered trade log, then roll the hops up into a ranked
-- transition map (which frontend feeds which, and how fast).
WITH ordered_swaps AS (
    SELECT
        tx_from,
        block_time,
        project AS current_frontend,
        LAG(project, 1)  OVER (PARTITION BY tx_from ORDER BY block_time) AS previous_frontend,
        LEAD(project, 1) OVER (PARTITION BY tx_from ORDER BY block_time) AS next_frontend,
        LAG(block_time, 1) OVER (PARTITION BY tx_from ORDER BY block_time) AS previous_swap_time
    FROM dex.trades
    WHERE block_time >= NOW() - INTERVAL '{{Days_Back}}' DAY
)
SELECT
    current_frontend,
    previous_frontend,
    COUNT(*) AS transition_count,
    AVG(DATE_DIFF('minute', previous_swap_time, block_time)) AS avg_time_between_hops_mins
FROM ordered_swaps
WHERE previous_frontend IS NOT NULL
  -- A journey is movement between frontends; ignore consecutive self-swaps.
  AND current_frontend != previous_frontend
GROUP BY 1, 2
ORDER BY transition_count DESC;

The same engine on four chains

The trace is one of four attribution vectors ClearTrace runs, and every one of them is deployed per chain across Ethereum, Base, Arbitrum, and Optimism from a single templated query with a {CHAIN} placeholder. The deliberate choice is what the template binds to: chain-specific tables (base.contracts, arbitrum.traces, and their peers) rather than the unified evms.* tables that carry every chain at once. The evms.* tables are enormous, and scanning them to answer a question about a single chain means paying for the other three. Reading the chain-scoped tables instead lands the same rows for roughly 60 to 70 percent less credit per run. A wallet's journey is reconstructed within each chain; the map is produced for all four.

Turning hops into behavior

The transition map is the primitive the higher-level views are built on. The same ordered-swap idea, widened, becomes a Sankey of routing edges (sender to entrypoint to underlying venue) and monthly wallet-cohort retention that tracks whether a frontend's users are still trading one, three, or six months after their first swap. A single frontend's "growth" reads very differently once you can see whether its new volume is genuinely new wallets or a churn loop rotating over from a competitor. That distinction is exactly what a foundation funding an ecosystem, or a protocol reporting its own traction, needs and rarely has.

Reading it honestly

Reconstructed sequence is an inference, not a logged fact, so the trace is careful about what it claims. It orders swaps strictly by block time within a single wallet on a single chain, and it does not silently stitch one wallet's activity across chains into a single fabricated timeline. Consecutive same-frontend swaps are excluded rather than counted as motion. Frontend names come from the same attribution layer that resolves the rest of ClearTrace, so a transition into "Unknown Proxy" is reported as an unknown, never dressed up as a named venue it was not. The output is a measurement of observed movement, with its limits stated, not a story about intent.

What It Shows

Behavioral reconstruction on data that was never designed to answer behavioral questions. The blockchain hands you a flat, sessionless log; window functions impose the ordering that a journey requires, and disciplined table selection makes that affordable across four chains instead of one. It is the same Rantum through-line as the rest of the ClearTrace engine: find the signal that is present but not stored, and extract it without inventing what the data does not support.

What It Proves to a Client

That we can build a behavioral analytics layer on top of raw, unordered event data, the kind most teams assume requires an instrumented product and a warehouse of sessions. Wallets, users, devices, transactions: wherever the records exist but the sequence connecting them does not, the same technique reconstructs it. For an L2 ecosystem or a protocol, that is the difference between a headline volume number and an actual picture of where users come from, where they go, and which of your growth is real. It runs today inside ClearTrace's live dashboard and public API.

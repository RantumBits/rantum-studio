Case Study Data Engineering CI as Infrastructure

The Ceiling Was Someone Else's

A production database kept as one SQLite blob on a Git branch, pushed twice a day. The pattern is cheap and it works, until the file approaches a limit you did not set. Four remedies, three of them wrong in ways you can measure, and a pipeline that ended red against the ceiling anyway.

Andrew Maury
• November 2026

AddressIntel, our predictive real-estate intelligence project, scraped municipal permit portals on a schedule and served what it found. It had no database server. The whole store was a single SQLite file, peninsula_intelligence.db, committed as a blob to a long-lived Git branch called data-store, checked out at the start of each run and pushed back at the end of it.

That branch carries 152 commits between 3 September and 4 November 2026: 120 of them the pipeline's own automated backup, the other 32 hand-run data commits. The project was wound down in November 2026 and nothing has run since 4 November 18:50 UTC, so everything here is measured against the store as it was finally left. The figures come from the canonical copy on data-store rather than from a development machine, and the piece says so again later, because that distinction turns out to be one of the pattern's running costs.

The pattern deserves part of its reputation. There is no instance to pay for, no connection string, no backup job, and the history of the data is the history of the branch. What no write-up of it told us is that once the file gets large the constraint stops being yours. It becomes a number set by whoever hosts the remote, enforced at the least convenient point in the run, and every obvious way around it is wrong in a way you can measure.

It is worth saying the ending first, because the rest of this reads differently without it. The pipeline's last twelve scheduled runs, from 29 October to 3 November 2026, all failed. Eleven of the twelve died on the project's own size gate, with the store at 92.27 MiB and 7.73 MiB of headroom left under the host's hard limit. The remedies below are real and they are measured. They were also, by the end, exhausted.

What the pattern bought

The shape is simple enough to describe in a sentence. A scheduled GitHub Actions workflow checks out data-store into a db_storage directory, copies the SQLite file into the working tree, scrapes, enriches, derives, pushes the new rows to the serving layer, copies the file back and commits it. The workflow is 1,138 lines. Most of that is not scraping.

What it genuinely bought is that the store is its own backup, restored once per run, with sixty-three days of versions retained for nothing. The second property, the one that looks like free real estate, is that anything the pipeline wants to remember between runs can be written into the file and ride to the branch with everything else, with no second system to provision.

That second one is a trap, and the project walked into it. The section after next is about how.

The number that was not ours

GitHub rejects any blob of 100 MiB or more at the pre-receive hook. The project's record of 15 September 2026 at 17:30 UTC has the push finally failing: 

remote: error: File peninsula_intelligence.db is 100.55 MB; this exceeds
GitHub's file size limit of 100.00 MB
 ! [remote rejected] data-store -> data-store (pre-receive hook declined)

The timing is the lesson rather than the limit. The save step is the last thing a sixty-minute run does, and the sync to the serving layer runs before it. So production kept receiving fresh rows while the canonical lineage stopped advancing, silently, and that run's scraped rows were lost. A failure at the end of the run is a failure that has already spent the run.

What pushed it over was not drift. By the project's account a change five days earlier had replaced a 25,000-row ceiling on the archive restore with a count-sized fetch, and the first run under it restored 40,322 archived permits the ceiling had been hiding, taking the store from 146,903 to 187,225 permits in one pass. The restore was working as designed. The consequence of it working was that the store began converging on an append-only archive, which is to say the file could only grow.

Four remedies, three of them closed with a number

This is the part of the pattern that nothing written about it prepares you for. Each of the obvious answers is plausible, and three are worse than the problem once someone puts a number on them. The measurements below are the project's own, recorded in the header of the compaction script at the time each option was ruled out; I have reproduced the end state they produced but not re-run the comparisons themselves.

  • Git LFS. Closed on arithmetic rather than taste. The repository is private on the free plan, which allows 1 GB of LFS bandwidth a month, against a roughly 90 MiB blob pushed twice a day. That exhausts the quota in under a week, and LFS stores every version whole rather than as a delta.
  • Compressing the blob. gzip -9 takes the file to 17.7 MiB, which reads like a five-fold win until you measure what it costs Git rather than the filesystem. Packed side by side, five consecutive raw snapshots occupy 19 MB, because Git deltas SQLite files extremely well. The same five gzipped occupy 96 MB. It trades a five-fold file win for a five-fold repository-growth loss, and slows every clone.
  • A plain VACUUM. The intuitive answer, and close to a no-op here. The freelist was empty at every recent commit, and VACUUM alone moved 90.16 MiB to 88.35. The file was full of live data rather than slack.
  • Changing the physical layout. The one that worked, and it touched no schema and no rows. The page size went from 4 KiB to 16 KiB, because the largest per-row payload averaged about 2,369 bytes and spilled into overflow chains whose tails were dead space: the enrichment table occupied 23.34 MiB on disk for 13.49 MiB of actual JSON, 40.8% of its pages unused. A 16 KiB page holds those rows inline, taking 90.16 MiB to 77.61 MiB. Then the two tables keyed on a composite text primary key, (city, permit_id) and (city, apn), were rebuilt WITHOUT ROWID, each having carried a full shadow copy of that key in an implicit autoindex, 5.68 MiB and 2.17 MiB, purely to find a rowid nothing in the codebase reads. That took it to 70.72 MiB.

Together, 21.6% with nothing lost. Both changes are verifiable on the final store, which reports a page size of 16,384, carries both tables as WITHOUT ROWID, and has a freelist of zero pages. A 32 KiB page was measured too, at 77.59 MiB against 16 KiB's 77.61, so the larger page bought 0.02 MiB and cost read amplification. That result is worth recording precisely because it is boring: it closes the question instead of leaving it to be re-proposed.

One claim in that script's own header does not survive contact with the code, and it is worth flagging because it is the kind of thing a reader would otherwise inherit. The header says the compaction is idempotent, a no-op once the layout is right. The function has a third rewrite trigger the header omits: it also rebuilds when at least 3% of pages are unused and that slack is at least 2 MiB, which is what a run does to a b-tree when it bulk-inserts. The in-code comment beside it is explicit that this is the case the first release missed. On 3 November it fired on a store whose layout was already correct, logging 3.1% of pages unused (2.89 MiB); reclaiming and then 92.27 to 92.27 MiB (0.00 MiB reclaimed): a full rewrite that returned nothing.

The remedy the guard forbids

Compaction buys a fixed percentage once. It does not change the slope, and against an append-only archive a fixed percentage is a delay. The real remedy was to decide what the working store is for and stop keeping rows outside that window.

An earlier note had ruled pruning out, and its reasoning was correct when written: a prune is self-defeating while the restore is additive, because the archive re-inserts what you removed on the next run. What made pruning viable was bounding the restore at a configured horizon date, 1 January 2023, on 15 September. What the objection could not foresee is that bounding the restore bounded one writer out of eleven. Three ingest loaders then put 78,803 pre-2023 rows into the store by hand, which is what tripped the size gate on 6 October before that run had scraped anything.

So the horizon stopped being one writer's rule and became the store's invariant: a filter applied to every loader at write time, and a sweep over the table on every run. There is a test that enforces this by discovering the writers rather than listing them, so a new loader fails it by existing. Measured through the compaction script on one commit, the sweep took 93.53 MiB to 75.61 MiB, and the permit table from 47.28 MiB to 29.36 MiB.

Which the regression gate is built to reject. A prune makes a total fall, and a falling total is the exact condition that fails a run. The two guards are in tension by construction, and the resolution is not clever: the one-time cleanup carries an explicit acceptance flag that records the reduction as deliberate and rebaselines. The drop is still legible in the stored metric history. The highest permit total it ever recorded is 198,608 on 5 October at 19:04 UTC; the lowest is 120,039 the following evening at 18:47. The store ended at 127,947.

The guard whose memory the branch erased

The regression gate exists because of a defect two snapshot guards could not see. Rows kept landing and per-city counts held while a placeholder overwrote a real valuation on every sync, and by the project's reckoning $794,618,780 of valuation obtained through public-records requests was erased over months with every run staying green. Nothing had recorded what the numbers were last run, so nothing could notice them shrinking.

The fix was a metric_history table written into the database itself, so it would ride to the branch for free. This is the obvious move under this pattern and it is where the pattern bites hardest, because for its first weeks the gate never compared anything at all. Every run printed that it had no prior record and that the gate would be live from the next run, and it never was.

Both persistence paths had failed, and they failed for opposite reasons. The sidecar JSON file was covered twice by .gitignore, and the checkout action cleans ignored files at the start of every run, so it was deleted before the run that would have read it. The in-database table failed because of the branch: the gate ran last, after the save step had already copied and pushed the file, and the next run's restore overwrote the working copy wholesale with the pushed copy that had no such table. The guard against an eight-figure silent loss was itself silently doing nothing, which is the precise failure mode it was built to catch.

The fix kept the property that made the gate safe and moved only the write: record the baseline before the save, save, then run the gate. The table's history starting on 16 September rather than at the branch's own beginning on 3 September is the fingerprint of that repair. It now holds 20,138 rows across 76 snapshots, per city and in total.

The transferable version is not about SQLite. If a guard's state lives inside the artifact your pipeline overwrites every run, the ordering of the write against the overwrite is the guard. Get it wrong and you have a gate that reports success and compares nothing.

Ordering, four more times

The same reasoning runs through the rest of the workflow once you look for it.

The horizon sweep was first placed in the derivation block at step 15, while the size gate is step 8, so on 6 October at 17:02 UTC a run died at the gate on a 93.53 MiB store while holding the rows that the step seven places later existed to remove. To be exact about the blast radius, because the lesson is more quotable than the incident: the misordering was introduced at 09:15 and corrected at 10:13 the same morning, and cost exactly one run. The principle is still the one worth keeping. A remedy downstream of the check that demands it is not a remedy.

Compaction happens before the copy, so the blob that goes up is the small one, and the early gate cannot do that job because the run's own bulk inserts happen after it. The final size check is deliberately duplicated immediately before the push, because a single run can add rows and the number that matters is the one being pushed. Failing there with your own message beats failing on the remote's pre-receive hook: it names the file, the size and the remedy inside the step's own log rather than as a remote: error: line in a 1,300-line run log.

Four gates sit at the very end, after the sync and after the save: source health, permit coverage, metric regression and a narrow scoring check. They are last for the opposite reason to everything above. A run that goes red has already persisted every byte it collected, and a red run that kept its data is the goal. The source-health gate exists because a city sat at 2 permits for weeks on a rejected portal login while the scraper printed a warning, returned an empty list and let the run report success, and that absence then rendered as "0 demo permits" in copy sent to an audience who would know it was false. It checks only failures a scraper knows about and refuses to infer breakage from a low count, since a quiet city and a broken scraper both yield zero. It is also deliberately slow to escalate: a failure is annotated on the first run, and the job only goes red once a source has failed a threshold number of a recent window of runs, or two sources break at once. That rule was added after a single scraper crash red a run in which everything else had worked.

There is one more guard worth stealing outright. The data-store checkout is allowed to fail without failing the run, so the save step first asks whether the directory is missing while the branch exists on the remote. If both are true, this run started from an empty database and pushing it would replace the whole backup with one run's worth of data. It bails. The push is a force push, so nothing else would have stopped it.

Two copies, one filename

The cost the pattern never stops charging is that a database you can copy is a database that gets copied.

On 15 September 2026 four separate published figures were wrong from a single cause: they were measured against the file on the development Mac rather than the canonical copy on data-store. Both files are called peninsula_intelligence.db and nothing on either said which was which. A classifier change was published as moving 37 rows in one city, when against canonical it moved 280 and a second city the claim never mentioned was missing from it entirely. A join rate of "3,417 of 3,447 APNs, 99.1%" was measured against a table that exists only on the dev machine, where the canonical figure is 0 of 3,447, and it reached a commit message and a public-facing log. An ingest's before-count was read as 57 when canonical already held 96. A committed test fixture was generated from the local copy and so covered 40,514 pairs of a 95,354-pair corpus, blind to the vocabularies it was missing.

The response was a provenance test rather than a naming convention, and it is two-sided on purpose so it cannot pass on a truncated or unreadable file. A database is canonical only when it carries a marker table that data-store has and the dev copy does not, and carries none of the seven tables only a development machine builds. Run against the two copies as they now stand it classifies both correctly: canonical holds 20 tables and the marker and none of the seven, the development copy holds 25 tables and all seven and no marker.

The divergence is not a rounding error. The canonical store is 92,487,680 bytes, 88.20 MiB, holding 127,947 permits. The development copy is 769,474,560 bytes, about 733.8 MiB, holding 228,011. Eight times the file for 1.8 times the rows, because only one of the two is under any pressure to stay small. Neither is a superset of the other, and the gap is wide in both directions: comparing them on the composite key, 121,776 permits are in both, 6,171 exist only on canonical and 106,235 only on the development copy. The canonical copy holds permits issued as recently as 4 November; the development copy stops at 13 October.

That is the honest accounting. The branch gives you a canonical copy for free, and then the ordinary act of working on the data produces a second one that is larger, fresher in some respects, staler in others, and indistinguishable by name.

How it actually ended

The last twelve scheduled runs, from 29 October 05:30 to 3 November 17:30, all failed. Eleven died at the size gate before scraping anything; the twelfth was the only one in the streak that reached the metric regression gate and failed there. Three runs after that went green, and then nothing ran again.

The gate's error text on 3 November is the fairest summary of the pattern anyone wrote: 

The data-store SQLite file is 92.27 MiB, over the 92 MiB gate and only
7.73 MiB under GitHub's 100 MiB blob limit. The save step at the END of
this run would be rejected by the pre-receive hook, after the Data Connect
sync had already published this run's rows, so the run is stopped HERE
instead, with nothing published and nothing lost. Compaction has already
been applied and was not enough: the store needs a real remedy (bound the
working store against the archive, or split it).

The guard did its job. It converted a push rejection at the end of the run into a cheap refusal at the start of it, which is the whole difference between losing an hour's scraping and not. But the store was over the project's own gate for six straight days, compaction had nothing left to give, and the horizon prune had bought roughly three weeks before growth caught up with it. The remedy the pipeline was asking for by then was not another percentage. It was to stop keeping the archive and the working store in the same file, which is a different architecture rather than a tuning pass.

What to take from it

  • A storage pattern you do not pay for has a limit you do not set. The 100 MiB blob ceiling is the host's number, not configurable, and it is enforced at the push rather than at the write.
  • Find out early or spend the run. The first failure arrived at the last step of a sixty-minute run, after the serving layer had already been updated. Gate the size at the start, where it costs a second, and again immediately before the push, where the number is real.
  • A remedy downstream of the check that demands it is not a remedy. The sweep sat seven steps after the gate it was written to satisfy. It cost one run, and only because someone noticed within the hour.
  • Close the obvious options with a number. LFS, gzip and VACUUM are each the obvious answer to somebody. One measurement apiece closes them, and writing the numbers down is what stops them being re-proposed.
  • Physical layout is the cheapest fifth you will find, and it is still only a fifth. Page size and WITHOUT ROWID cut 21.6% with no schema change and no row loss. On a store converging on an append-only archive, that is a delay rather than a fix, and the run history says so.
  • Expect your guards to contradict each other. A gate that forbids a shrinking table and a prune that keeps you under the ceiling cannot both be satisfied, and the resolution is an explicit recorded acceptance rather than a weakened gate.
  • A guard whose state lives in the artifact you overwrite every run is an ordering problem. Writing the baseline after the save meant the next restore erased it, and the gate reported success while comparing nothing for weeks.
  • Name the copies. Two files with the same name and different contents will be confused, by careful people, on the same day. A two-sided provenance test is cheap, and a convention is not enforcement.
  • Know the exit condition before you start. The pattern is excellent early and has a hard end, and the end is a migration you would rather schedule than discover. Decide in advance what size triggers it.

A Git branch was a defensible place to keep this database, and it held one for sixty-three days without an instance to pay for. What it charged was not storage. It was the work of discovering, one red run at a time, where somebody else's limit sat, which of your own guards would fight you on the way to it, and that the file you were protecting had quietly become two.

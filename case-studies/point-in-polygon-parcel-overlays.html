Outside the Polygon, or No Polygon at All

The spatial join is the easy part. Four times, an overlay returned a confident answer about a parcel where the correct one was unknown.

Andrew Maury
• October 2026

AddressIntel, our predictive real-estate intelligence project, fuses San Mateo and Santa Clara County GIS layers onto parcels: zoning, fire hazard severity, flood, fault, liquefaction, landslide, farmland, Williamson Act contracts, Coastal Zone. The mechanism is a point-in-polygon lookup against each county's ArcGIS REST endpoint, and then a derived answer about what can legally be built. The scored table holds 489,915 parcels across 16 cities.

Writing the lookup took an afternoon. Every expensive mistake since has come from the same place: the pipeline had a definite answer to give and gave it, where something weaker was called for. Four of them are below. Two are the pure form, a confident answer standing in for one the pipeline did not have: a layer emptied upstream that read as a clean negative, and a fallback rule chosen to be conservative that was not conservative where it mattered. The other two are its neighbours, and they are worth separating rather than folding in. One is a confident answer that was simply the wrong answer, a polygon hit reported as a legal conclusion it does not support. One is a refusal that survived, a city declining to assess a parcel, which the pipeline carries instead of filling in, and which a careless query nearly flattened anyway.

The fixes converge even where the faults differ: make the weaker answer representable, and keep it distinct from no.

A sibling piece, Scraping Adversarial Municipal Portals, covers the same shape in a different layer: a source that answers cheerfully and wrong, a rejected login returning an empty list. That one is about scraping HTML portals and detecting silent truncation. This one is about the spatial join and what a polygon lookup is entitled to conclude.

What the lookup is

For each parcel centroid the pipeline posts the point to the county's layer with geometryType=esriGeometryPoint and spatialRel=esriSpatialRelIntersects, and reads back either the intersecting feature's attributes or a count. San Mateo County's layers sit on a self-hosted gis.smcgov.org MapServer, and two of its towns publish their own zoning from their own ArcGIS organisations because the county layer answers NO DATA ASSIGNED for them. Santa Clara County's sit on ArcGIS Online. Counting only the scoring path there are fourteen distinct hosts, plus those two town organisations and one city delivered as a local shapefile: FEMA, the counties, and seven cities that publish their own. The enrichment module that holds these is 2,223 lines, and most of that is neither geometry nor SQL.

The reliability work is the visible part. The Santa Clara host answers bursts with read timeouts and connection resets, so calls to it pass through a two-permit semaphore, two attempts with a jittered backoff sleep between them, and a staggered release so threads queued on the semaphore do not all fire the instant a slot frees. Above that sits a circuit breaker that opens after three consecutive call failures and skips the rest of the run. The breaker's own counters had to be put under a lock: without one, concurrent threads each crossed the threshold independently and logged the same trip line several times a few milliseconds apart, which is how the race was found.

None of that is the interesting failure. A timed-out call is loud. The failures below were all quiet.

A layer can be emptied without erroring

Santa Clara County republished two of its planning layers with zero rows countywide on 25 September 2026. The pipeline asked one of them, the Agricultural Preserves layer, whether each point fell inside a preserve, using returnCountOnly. An empty hosted layer answers that query perfectly well. It returns a count of zero. So the lookup did not error, did not time out, and did not trip the breaker. It simply began answering no for every parcel in the county, in the same shape as a true negative, and it would have gone on doing so indefinitely.

This is the failure mode worth naming, because a spatial join over someone else's layer is exactly where it hides. A join has three possible answers and the API gives you two. There is inside the polygon, outside the polygon, and no polygon to be inside of, and the third arrives wearing the second's clothes.

The discriminator we ended up with is a quirk of the hosting. A zero-row layer answers a bare returnCountOnly request fine, but rejects with HTTP 400 and Cannot perform query. Invalid query parameters. any request that both filters by geometry and materialises features. So when a feature fetch fails, the collector asks the layer for its unfiltered total row count. Zero means the layer really is empty upstream, and zero coverage is the correct report. Anything else, including a count it cannot obtain, leaves the layer marked unknown so the run still reads as failed: 

if _layer_row_count(url) == 0:
    print(f"    WARN {label}: layer is EMPTY upstream (0 rows countywide) "
          f"— reporting zero coverage, not a fetch failure ({e})")
    return []
print(f"    WARN {label}: fetch failed ({e}) — layer treated as unknown")
return None

An empty list and None are different values, deliberately, and every caller has to handle both.

That discriminator sits on the bulk collection path, and it is worth being exact about which path it does not sit on. The per-point lookups the listing-level enrichment uses still ask returnCountOnly one parcel at a time and still end in return c > 0, with no row-count probe. The farmland, Williamson Act and county SB 9 layers all go through that path, and every one of them would still read an emptied layer as a clean negative. The ag-preserve signal was not fixed by teaching that path the difference. It was fixed by retiring the live lookup and reading a snapshot taken before the layer was emptied, which the file itself qualifies: it was recovered from pre-emptying caches, two cities' caches had already been overwritten, and it is complete for the scored footprint rather than countywide. The general lesson survives the specific fix, and so does the exposure.

A polygon hit is not a legal conclusion

The second failure is the one that produced wrong numbers rather than silence. SB 9, California's urban lot split law, disqualifies a site that is prime farmland or farmland of statewide importance. Santa Clara County publishes several agriculture-related layers, and for a while the pipeline folded three of them into one primeFarmland flag: the state farmland mapping, Williamson Act contracts, and agricultural preserves. A hit on any of them disqualified the parcel as prime farmland.

They are three different things, and only one of them is the statutory category. Measured against the scored table today, after the three were separated on 28 September 2026:

  • 17 parcels are prime farmland or farmland of statewide importance, the category the statute actually names. 15 in San Jose, 2 in Los Gatos.
  • 216 parcels are under a Williamson Act contract. That is a tax-assessment contract restricting land to agricultural use. It is not prime farmland, and strictly it is not one of the statutory site criteria either.
  • 4,107 parcels sit in an agricultural preserve, 2,626 of them in Los Gatos and 1,228 in San Jose. An ag preserve is neither prime farmland nor a voter-approved agricultural protection measure, so it is not an SB 9 bar at all.

The three overlap only partly. All 216 Williamson parcels are also inside an ag preserve, but 16 of the 17 prime-farmland parcels are in neither other set, and the union of the three labels is 4,123 parcels today. The repository's record of the fix puts the old flag's reach at 4,104 Santa Clara parcels blocked as prime farmland, 104 of them ordinary San Jose tract houses the state farmland map classifies as urban and built-up land. That historical set is not the same set as today's union, because the old flag read the farmland layer unfiltered and today's reads only the two statutory categories. Of the 4,123, exactly 233 now carry a farmland-family disqualifier and only 17 of those carry the one the column used to give. The rest of the union is not thereby buildable: 3,157 of the 4,123 are still SB 9-blocked, almost all of them on lot size, flood, fire or fault rather than on anything agricultural.

The Williamson parcels are still blocked, under their own name. The contract forbids the housing project for the length of its rolling term, so reporting such a parcel as eligible would be wrong in the more dangerous direction: it would tell someone they can split land they legally cannot. Blocked, with its reason named accurately, is the correct report, and the reason string is what carries the accuracy.

Two layers of answer, because one is not enough

The separation that makes this expressible is that the derivation emits two lists rather than one verdict. sb9BlockReasons holds statutory disqualifiers only. developmentBlockers holds everything that raises cost, risk or process friction, disqualifying or not. Several signals appear in one list and not the other, and the choice is load-bearing each time:

  • Fire. Only a Very High Fire Hazard Severity Zone is statutorily SB 9-disqualifying. Plain High raises construction and insurance cost and bars nothing. 5,214 parcels are Very High and blocked; 10,780 are High and carry a cost blocker only.
  • Coastal Zone. SB 9 and state ADU law do not override the Coastal Act, so a Coastal Development Permit is still required. The parcel is encumbered without being ineligible, so the signal is a development blocker and never a block reason.
  • Liquefaction and landslide. 201,670 and 14,085 parcels respectively. Neither bars anything; both change what building there costs. Putting them in the disqualifier list would have made two fifths of the coverage area read as undevelopable.

Writing the overlay as a Coastal Zone hit flips eligibility would be the same defect class as the farmland flag, just in the other direction. The accurate statement is narrower and less quotable: the overlay changes what the parcel costs and how long it takes, and sometimes, for specific named layers, it changes what is permitted.

One figure here cuts against the way this layer gets described, including in our own earlier notes. Across the 4,004 listing-level enrichment rows, exactly one carries a Coastal Zone hit. The covered cities are inland. The layer is correct, queried, and almost entirely inert, and a case study that led with it would be dressing up a single row as a pipeline feature.

The fallback that was not conservative

The second half of the pipeline is rules as code. A screening signal we care about is how built out a lot is, living area over allowable floor area, which needs each jurisdiction's floor-area rule. Those are 19 jurisdictions in a table of formulas, every entry carrying source, asOf and confidence: 9 high, 7 medium, 3 estimated, researched between 30 June and 3 September 2026. Only one of the three marked estimated is a bare fallback, and it is the interesting one: it applies the default ratio of 0.40 to lot coverage and multiplies by a stories factor, which lands at roughly 0.52 effective, above the curated cluster rather than below it. The other two carry a partial curation that the confidence field declines to promote, one capped from a table in the town's own code with the slope half still missing.

The default of 0.40 was chosen to be conservative. It sits at the low end of the curated cluster, so for a city near that cluster it understates allowable area, which biases against false this lot has headroom signals. That reasoning is sound and it is not a safety property, which is a distinction worth the paragraph it costs.

Two towns were curated on 3 September 2026 after an audit, and until that day both inherited the default. One has a ratio of 0.25 tapering to 0.15 above an acre, against which the default overstates allowable floor area by 1.60 times on a half-acre lot and 2.33 times at 200,000 square feet. The other is worse by an order of magnitude, because its caps are absolute rather than proportional: the repo records the default overstating it by 2.7 times at the minimum R-1 lot, 5.8 times at an acre and 29 times on a ten-acre parcel. In both the error is largest exactly where lots are biggest and a teardown call carries the most money. An estate town is the shape a flat default gets most wrong, and it is also the shape where the signal gets used hardest.

The lesson is not that the default was badly chosen. It is that a default is an answer. Uncurated should read as unknown, not as safe, and the confidence field exists so that a caller can tell the difference instead of inheriting our optimism.

When the city itself declines to answer

The best-behaved source in this pipeline is the one that publishes its own uncertainty. Palo Alto's assessor parcel layer carries a floor-area field, and for some parcels it does not state a figure. It says instead that it cannot assess one, naming a creek, a flag lot or a right-of-way. That is a city telling you a constraint binds that it will not quantify.

1,317 of the 20,849 scored Palo Alto parcels carry the resulting far_not_assessable blocker. The arithmetic for those parcels is still run and still correct for the lot, and the flag rides alongside it to say that something we do not model is known to apply. That is a different statement from a missing value, and it is more useful than either a number or a blank.

Extracting it took two tries, and the first try is instructive. Matching the field loosely on the phrase can't assess also catches a different sentence the same layer uses, which means the district is not residential rather than that a physical constraint binds. The loose predicate pulled 7,593 parcels where the specific one pulls about 1,359, so more than four fifths of the matches were a different statement entirely. Two sentences in the same column, both reading as absence of a number, meaning unrelated things.

We ingest that layer's judgement and not its numbers, on purpose. Its floor-area values agree with our own formula for Palo Alto on 99.23 percent of 14,044 parcels, checked 28 August 2026, with the residual explained by rounding in its acreage strings. That agreement is what makes the layer trustworthy on the question, and it is also why its figures are not worth importing: they are our own arithmetic coming back to us. The non-redundant content is the refusal.

Unknown is also the resume cursor

Keeping unknown distinct from no stops being an honesty argument once the backfill runs. The overlay backfill walks already-enriched rows with a four-worker pool, and rows whose lookups time out are left undone and picked up next run. What makes that work is that a failed lookup writes None rather than False. The resume predicate reads those nulls as outstanding work: 

# Only mark the SCC pass done when BOTH resolved; a None in either
# means that lookup errored -> retry next run.
if r["city"] in SCC_CITIES and prime is not None and wact is not None:
    payload["sccPrimeChecked"] = True

If a transient ArcGIS timeout had been recorded as a negative, the pipeline would be self-consistent, would converge, and would be wrong, with nothing left in the data to indicate which rows had never actually been asked. In the current enrichment rows, 1,511 have an unresolved corner-lot lookup, and the resume predicate names that field, so every one of them will be asked again next run. Those nulls are the queue rather than gaps in the dataset.

A second set of nulls looks identical and is not. 221 rows carry an unresolved farmland value against 13 positive and 3,770 negative, and all 221 are San Mateo County listings. The backfill sets farmland to null for that county unconditionally, because no state farmland source is wired for it, so no run will ever resolve them. Both sets are nulls and only one is work. A null says that a value is not known; it does not say whether anyone is still going to look, and a pipeline that wants to act on the difference has to record that separately.

What this pipeline still does not know

Three limits belong on the page rather than in a footnote.

Zoning is mostly absent at the listing level. 3,055 of the 4,004 enrichment rows have a null GIS zoning value, and a further 782 carry the county layer's own NO DATA ASSIGNED sentinel, which the backfill treats as absent. By the pipeline's own test, 3,837 of 4,004 have no usable zoning and 167 do. Without it the derivation cannot reach a hard eligible and returns likely instead, which is why 109,132 of the 489,915 scored parcels sit in that middle state. Absence of a block reason means no disqualifier was found rather than that eligibility was established.

A resume cursor can mark a new question answered. Writing this piece turned up a fifth instance of its own subject, in the mechanism the previous section praises. The Williamson Act check became its own signal on 28 September 2026 and the backfill was updated to require it, but rows marked complete under the previous rule were never re-asked, because the predicate that would re-ask them is the one reading the stale mark. Measured on 28 October 2026, before the fix: 1,943 rows marked as having completed the farmland pass, and not one williamsonAct value anywhere in the 4,004. Every count elsewhere on this page is from that same measurement and is unaffected, because the parcel-scoring path does not use the mark. The parcel-scoring path, which the counts above come from, is unaffected; it does not use that mark.

The fix merged on 28 October 2026, and the repair is more interesting than the fault. The obvious version tests whether the row carries the field at all, and that version is wrong in a quieter way: a failed lookup writes a null, so the presence test would be satisfied by the error and lock it in permanently. The completeness test has to mirror the write-back condition, both answers present and not null, which is the same rule the corner-lot retries already follow. A mark records that a pass ran rather than that it answered what the pass asks today, and a field added afterwards has to be able to invalidate it. The rows themselves are still owed their answer: the fix makes the next scheduled run ask the question, and until that run lands the values are missing from the listing layer exactly as described.

These counts come from the enrichment copy of the database, which is the only copy that has them. AddressIntel keeps two copies of a file with the same name: a canonical one that the application serves, and a working one on a development machine. They are not supersets of each other, and on 15 September 2026 four separate published figures were wrong from exactly that confusion. The provenance test written in response identifies a canonical database by requiring a marker table it carries and no marker tables only a development machine builds. The parcel scoring table is in the second set, named in the test as a development marker because it is never synced. The listing enrichment table is not named in either set, so the test neither confirms nor denies it; it travels with the first because the two sit in the same file. So every figure in this piece is measured on that copy by necessity, and no canonical counterpart exists to check them against. Saying so is the only available form of provenance here.

What to take from it

  • A spatial join has three answers. Inside, outside, and no layer to be inside of. If your schema cannot hold the third, you will serve it as the second.
  • Check that a negative source can still produce a positive. An upstream layer republished empty answers a count query cheerfully. Something in the pipeline has to be able to notice that a signal which used to fire has stopped firing entirely.
  • Keep the overlay hit and the legal conclusion in different fields. A polygon tells you where a parcel is. A statute tells you what that implies, and usually it implies less than the layer's name suggests.
  • Carry source, as-of date and confidence on every rule. Rules as code without provenance is a number with no way to tell curated from guessed, and the guess is where the large errors live.
  • Treat a default as an answer. Conservative in the typical case is not conservative in the tail, and the tail is where the decision is expensive.
  • Preserve a source's refusal to answer. It is information, it is cheap to carry, and it is the one thing a downstream model cannot reconstruct.

The overlay does change the answer. What took longest to get right was the smaller claim underneath it: knowing when the overlay has not answered at all.
